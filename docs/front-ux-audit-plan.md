작성일: 2026-09-27 (Asia/Seoul)
대상: Modal GUI React/Tauri 프론트
기준: `ux-audit`, `ux-flow-audit`

## 1. 조사 범위와 판단 기준

이번 조사는 화면 모양만 보는 검토가 아니라, 사용자가 목적을 달성하는 동안 화면이 실제 시스템 상태·비용·계정·복구 가능성을 정확히 표현하는지 확인하는 작업이다. 다음 네 가지 목표 모드를 기준으로 조사했다.

| 목표 모드 | 실제 사용자 목표 | 대상 화면 |
| --- | --- | --- |
| 창작 | 아이디어를 프로젝트로 만들고 소재·노드·샷을 구성한다 | 제작 스튜디오, 새 작업 |
| 실행 | 선택한 계정과 도구로 생성·렌더를 실행한다 | 노드 Inspector, 작업 큐, 편집·모션 |
| 검토 | 결과 후보를 비교하고 편집·내보내기한다 | 스토리보드, 타임라인, 결과물 |
| 운영 | 계정·연결·비용·설정을 확인하고 복구한다 | 사용량, 연결 관리, 설정 |

실제 경로는 다음 소스와 저장소를 서로 대조했다.

- 제품 의도와 상태 원칙: `README.md`, `docs/creative-studio-architecture.md`, `docs/next-work-plan.md`, `docs/renderer-plugins.md`
- 화면: `src/App.tsx`, `src/pages/**`, `src/EditPage.tsx`, `src/UsagePage.tsx`, `src/studio/**`, `src/styles.css`
- 네이티브 경계: `src-tauri/src/main.rs`, `jobs.rs`, `studio_run.rs`, `usage.rs`, `connections.rs`, `database.rs`
- 브라우저 미리보기: `npm run dev`와 Playwright CLI로 기본 진입점 및 모든 사이드바 화면을 확인

현재 기준 작업 트리에는 이 문서와 무관한 기존 변경이 있다. `docs/incidents/2026-09-27-editorial-rainbow-clips-drift.md`, `tools/assemble_ref2v_episode.py`, `tools/assemble_sky_episode.py`, `tools/rainbow_editorial_ae.jsx` 및 `.codex/`는 이번 계획 작업에서 수정하지 않는다.

## 2. 확인된 현재 구조

앱은 `Studio`를 기본 화면으로 열고, `Generate`, `Jobs`, `Edit`, `Results`, `Usage`, `Connections`, `Settings`를 `App.tsx`의 로컬 `page` 상태로 전환한다. Studio 안에는 좌측 노드·소재 패널, 중앙 React Flow 캔버스, 우측 Inspector/대화 패널, 하단 타임라인·스토리보드가 동시에 존재한다.

주요 상태의 권위는 다음과 같다.

| 상태 | 권위 있는 저장소·경로 | 현재 UI 반영 |
| --- | --- | --- |
| 일반 작업 | SQLite `jobs`와 `job_events`, worker event | 앱 시작 시 최근 작업을 보충하고 `worker-event`로 갱신한다. `src/App.tsx:22-83` |
| Studio 실행 | SQLite `studio_runs`와 `jobs`, `studio_run` 이벤트 | `runController`가 실행·완료·실패·재동기화를 담당한다. Tauri 명령은 `src-tauri/src/main.rs:94-99`에 있다. |
| 프로젝트·소재 | `studio_projects`, revisions, assets 및 브라우저 임시 소재 | Zustand 문서와 Tauri 저장을 함께 사용한다. `src/studio/store.ts:196-248` |
| 계정·사용량 | `modal_profiles`, `usage_records`, Modal billing report | `UsagePage`가 실제 계량·예산·마지막 동기화 상태를 구분하려고 한다. |
| 연결·도구 | `connections`, `connection_tools`, ChatGPT 계정 | `ConnectionsPage`에서 연결 테스트·도구 목록·로그인 상태를 표시한다. |

문서와 구현에서 이미 지켜지는 좋은 경계도 있다. 시작 시 중단된 작업과 Studio 실행을 종료 상태로 정리하고(`src-tauri/src/main.rs:47-53`), 비용이 없는 실행을 0으로 확정하지 않으며(`src/studio/Inspector.tsx:920-945`), `prepared`와 실제 렌더 완료를 구분한다(`src/studio/runController.ts:613-628`). 이후 개선은 이 경계를 유지하면서 사용자 흐름을 단순화해야 한다.

## 3. 실제 사용 흐름과 현재 문제

### 3.1 Studio에서 프로젝트를 만들어 결과를 내는 흐름

목표 흐름은 다음이다.

`프로젝트 생성 → 소재·브리프·무드보드·스토리보드 추가 → 노드 연결 → 노드 실행 → 결과 후보 선택 → 타임라인/내보내기`

현재 구현은 프로젝트 생성과 자동 재진입까지 있으며(`src/studio/StudioPage.tsx:60-98`, `100-124`), 노드 실행·후보 선택·취소·재다운로드도 각각 존재한다(`src/studio/Inspector.tsx:412-498`). 그러나 첫 화면부터 좌측 팔레트, 빈 캔버스, 우측 설정, 타임라인, 스토리보드가 한 번에 노출된다. 브라우저 확인 화면에서는 작업 대상이 비어 있을 때도 다섯 영역이 동시에 공간을 차지해, 사용자가 다음에 무엇을 해야 하는지와 현재 선택된 작업이 약해진다.

핵심 문제는 다음과 같다.

- **P1 / 창작 / Tauri와 브라우저 미리보기**: Studio가 실제로는 작업 공간인데 처음에는 노드·샷·소재가 모두 0인 상태로 여러 보조 패널이 열린다. 첫 행동을 `노드 추가`, `소재 가져오기`, `샷 추가` 중 하나로 좁히는 안내와 패널 우선순위가 필요하다.
- **P1 / 창작·실행 / Tauri**: 노드 카드의 `실행`과 Inspector의 `실행`이 같은 결정을 두 번 노출한다(`src/studio/NodeCard.tsx:147-165`, `src/studio/Inspector.tsx:472-485`). 선택된 노드의 세부 설정을 확인해야 하는 경우만 Inspector의 실행을 남기고, 일반 상태에서는 하나의 주 CTA로 통합한다.
- **P1 / 검토 / Tauri**: 실행 결과·후보·실행 기록·비용이 우측 패널에 모여 있고, 상단의 내보내기는 전체 문서 내보내기다. 결과를 확인하고 다음 행동을 결정하는 경로가 좁은 Inspector 안에 묻히므로 `결과 확인 → 후보 고정 → 다음 노드/스토리보드`를 한 흐름으로 재배치한다.
- **P1 / 운영·복구 / Tauri**: `dirty`, `saveState`, `saveError`는 Store에 있지만(`src/studio/store.ts:49-52`, `542-551`), 프로젝트 나가기 동작은 저장되지 않은 변경을 확인하지 않고 `closeProject()`를 호출한다(`src/studio/StudioPage.tsx:154-162`). 저장 중·저장 실패·저장되지 않은 변경·나가기 확인을 별도 상태로 만든다.
- **P1 / 데이터 보호 / Tauri**: 프로젝트, 노드, 소재, 샷, 템플릿, 연결 삭제 버튼에 확인 또는 undo가 없다(`src/studio/StudioHome.tsx:83-88`, `src/studio/Inspector.tsx:279-284`, `740-746`, `907-914`, `src/pages/ConnectionsPage.tsx:303-315`). 실행 기록과 소재 연결을 남기는 보관 정책과 영구 삭제 정책을 구분하고, 파괴 동작에는 영향 범위와 복구 방법을 보여준다.
- **P2 / 정보 계층 / Tauri**: 빈 캔버스, 타임라인, 스토리보드, Inspector가 각각 비슷한 안내 문장을 보여준다. `src/studio/StudioPage.tsx`의 빈 캔버스·타임라인·스토리보드 상태와 `src/studio/Inspector.tsx:948-950`의 프로젝트 안내를 한 문장 체계로 정리한다.

### 3.2 일반 생성에서 큐와 비용을 확인하는 흐름

목표 흐름은 다음이다.

`생성 모드 선택 → 입력·계정 검증 → 실행 요청 → 큐에서 상태 확인 → 결과·비용 확인`

현재 생성 폼은 활성 계정을 고르고 입력을 검사하며(`src/pages/GeneratePage.tsx:33-39`), 제출 시 로컬 작업을 먼저 `QUEUED`로 만든 뒤 Tauri 명령을 호출한다(`src/App.tsx:85-136`). 작업 큐는 상태·단계·오류를 보여주지만(`src/pages/JobsPage.tsx:6-42`), 행은 클릭되지 않고 중지·재시도·상세 보기 CTA도 없다.

- **P0 / 실행 / 브라우저 미리보기**: `App.submit`은 브라우저에서도 작업 행을 먼저 추가하고, `isTauri`가 아니면 Tauri 호출 없이 `Jobs`로 이동한다(`src/App.tsx:107-123`, `src/App.tsx:136`). 결과적으로 브라우저에서 실행 버튼이 동작하는 것처럼 보이고 작업이 영원히 대기 상태로 남을 수 있다. 미리보기는 모든 변경 CTA를 비활성화하고 “Tauri 앱에서 실행” 이유와 확인 가능한 예시 상태만 보여준다.
- **P1 / 실행·복구 / Tauri**: 큐 화면의 `작업 큐`는 계정·원격 실행·결과·비용으로 이어지는 상세 진입점이 아니다. `src-tauri/src/main.rs:63-66`에는 생성·시작·목록만 공개되어 있고, Studio에만 취소·재다운로드가 있다(`src-tauri/src/main.rs:94-99`). 일반 작업에도 취소·재시도·원격 상태 확인의 capability를 정의하고, 제공할 수 없는 동작은 이유를 표시한다.
- **P1 / 상태 진실성 / Tauri**: `worker-event`가 현재 메모리에 있는 작업만 갱신한다(`src/App.tsx:43-81`). 이벤트를 놓친 작업이나 이벤트가 먼저 도착한 작업은 부모 목록과 다시 조정되지 않는다. 생성·단계 변경·완료·실패·취소·다운로드 재시도마다 SQLite 확정 → 이벤트 → 목록 재조회 순서를 명시한다.
- **P1 / 구현 상태 노출 / Tauri**: 작업 행에 `job.id`가 그대로 노출되고(`src/pages/JobsPage.tsx:30-40`), Studio 실행 상태에는 내부 stage가 붙을 수 있다(`src/studio/NodeCard.tsx:142-146`). 사용자가 복구에 필요한 경우만 “세부 정보”로 숨기고 기본 행은 이름·상태·다음 행동 중심으로 만든다.
- **P1 / 운영 / Tauri**: 사용량 화면은 계정·예산·실제 계량을 구분하는 기반은 있지만, 생성 화면의 계정 선택, 큐의 실행 계정, 사용량의 비용 행을 한 번에 이어 주지 않는다. 작업 상세에 선택 계정, 원격 식별자, 비용 상태(실제·추정·미확인·반영 대기)를 같은 용어로 표시한다.

### 3.3 연결·계정·워크플로 운영 흐름

목표 흐름은 다음이다.

`연결 등록 → 테스트 → 도구 확인 → 필요한 도구 활성화 → 실제 호출 검증`

그리고 ChatGPT는 `로그인 시작 → 브라우저 인증 → 콜백 대기 → 완료/실패/취소/만료 → 재로그인` 흐름이다. 현재 화면은 이 상태들을 대부분 표시하고 로그인 만료 시간을 보여준다(`src/pages/ConnectionsPage.tsx:137-191`, `464-477`).

- **P1 / 운영 / 브라우저 미리보기**: 연결 추가·워크플로 등록·ChatGPT 로그인 버튼이 브라우저 미리보기에서도 활성화되어 있다. 화면 상단에 Tauri 전용 배지를 두고 저장·테스트·로그인·삭제를 모두 capability 기반으로 차단한다.
- **P1 / 데이터 보호 / Tauri**: 연결·워크플로 삭제는 즉시 실행된다(`src/pages/ConnectionsPage.tsx:115-121`, `303-315`). 삭제 전 사용 중인 프로젝트/노드와 도구 수를 알려주고, 연결을 비활성화하거나 보관하는 경로를 먼저 제공한다.
- **P1 / 운영 / Tauri**: 연결 한 화면에 MCP 등록, ChatGPT 계정, 워크플로, 정리 영역이 긴 세로 목록으로 누적된다. 목표가 다른 세 영역을 탭 또는 단계형 섹션으로 나누고, 기본 진입은 현재 필요한 운영 작업 하나만 강조한다.
- **P2 / 문구 / Tauri**: “등록”과 “실행 검증”을 구분하는 설명은 올바르지만 여러 위치에서 반복된다. 상태 chip에 의미를 담고 상세 설명은 한 곳으로 줄인다.

### 3.4 편집·결과·설정 흐름

편집 화면은 소스 읽기 → 스토리보드 선택/자동 채우기 → 분석·렌더 → 결과 확인 흐름이고, 결과물 화면은 Tauri의 실제 `deliverables` 파일을 읽는다. 브라우저에서 두 화면이 실제 파일을 읽을 수 없다고 표시하는 점은 정직하다(`src/EditPage.tsx:79-85`, `src/pages/ResultsPage.tsx:14-24`).

- **P1 / 검토 / Tauri**: 편집과 Studio 타임라인이 서로 다른 편집 모델을 갖고 있어 사용자가 어느 화면에서 최종 길이·타이포·렌더를 결정하는지 혼동할 수 있다. Studio 타임라인을 기준으로 할지 레거시 편집 화면을 결과 내보내기의 보조 도구로 둘지 먼저 결정한다.
- **P1 / 실행 / 브라우저 미리보기**: 편집 화면의 렌더 버튼과 소스 새로 읽기는 Tauri 전용 데이터에 의존하지만 화면에서 일반 버튼으로 보인다. 읽기 전용 미리보기 규칙을 동일하게 적용한다.
- **P2 / 구현 상태 노출 / Tauri**: 결과 화면은 경로를 바로 노출하고 “탐색기에서 보기”를 제공한다(`src/pages/ResultsPage.tsx:31-39`). 경로는 상세 정보로 이동시키고 기본 결과 카드는 파일명·생성 시각·결과 상태를 먼저 보여준다.
- **P2 / 운영 / Tauri**: 설정 화면이 현재 경로와 런타임 문자열을 나열하지만 사용자가 바꿀 수 있는 설정과 진단용 사실이 구분되지 않는다. 변경 가능한 설정, 읽기 전용 환경 정보, 문제 해결 진단을 세 그룹으로 나눈다.

## 4. 공통 결함

### 4.1 브라우저 미리보기와 Tauri capability 경계

`ResultsPage`와 일부 로더는 Tauri가 아니면 경고를 보여주지만, 생성·연결·사용량 계정 추가·편집 렌더는 동일한 전역 capability 정책을 공유하지 않는다. `src/lib/tauri.ts`에 `isTauri`만 흩어 사용하지 말고 다음 capability를 한 곳에서 계산한다.

| capability | 브라우저 미리보기 | Tauri |
| --- | --- | --- |
| 문서 임시 편집 | 허용, 브라우저 저장소임을 표시 | 허용, SQLite 저장 |
| 프로젝트·소재 영구 저장 | 차단 또는 임시 상태 | 허용 |
| Modal/ChatGPT/MCP 호출 | 차단 | 계정·연결 상태에 따라 허용 |
| 로컬 렌더·탐색기 열기 | 차단 | 도구·경로 상태에 따라 허용 |
| 샘플 상태·화면 탐색 | 허용 | 허용 |

버튼 disabled만으로 끝내지 말고, disabled 이유와 “Tauri 앱에서 열기” 같은 다음 행동을 제공한다. 브라우저에서 임시 작업을 만든다면 큐가 실제로 실행되지 않는다는 사실을 행에 표시하고, `QUEUED`를 운영 작업처럼 보이게 하지 않는다.

### 4.2 반응형·입력·접근성

현재 `body`에 `min-width: 1050px`가 있고(`src/styles.css:13`), Studio 좌측 244px·우측 332px 고정 패널이 있다(`src/styles.css:358-390`). 930px 브라우저 확인 화면에서 수평 스크롤이 생겼고, 상단 프로젝트 목록 버튼과 한국어 설명이 세로로 압축됐다.

추가로 입력 요소에는 focus 스타일이 있지만 전역 `:focus-visible`, reduced motion 정책, 대화상자 포커스 관리가 없다. 아이콘 버튼은 대부분 `title`을 갖지만 삭제·이동·축소 같은 핵심 동작의 키보드 순서와 포커스 복귀를 화면별로 검증하지 않았다.

### 4.3 상태·로딩·오류·복구

- 사이드바의 `mallagaenge / main`, `PIPELINE READY`, `Modal L40S / YuE2`, `LOCAL CORE`는 실제 연결·워커 상태와 관계없이 고정 문구로 렌더된다(`src/App.tsx:149-163`). 정상 상태를 상시 보여주기보다 장애·재연결·인증 만료·읽기 전용 상태에서 필요한 정보만 노출한다.
- Studio Inspector가 템플릿과 비용 요약 로딩 오류를 조용히 무시한다(`src/studio/Inspector.tsx:808-824`). 작업은 계속할 수 있어도 재시도·마지막 확인 시각·읽기 실패 상태를 표시해야 한다.
- 앱 시작 시 최근 작업 로드 실패는 빈 catch로 사라진다(`src/App.tsx:28-38`). 마지막 정상 목록과 “재시도”를 보존하고, 초기 로드와 백그라운드 재조정을 다른 로딩 상태로 표현한다.
- 긴 Modal/렌더 작업은 시작·원격 연결·다운로드·완료·실패·비용 반영 대기의 상태를 분리해야 한다. determinate percent를 계산할 근거가 없을 때는 단계와 경과 시간만 표시한다.

### 4.4 시각 계층과 성능

현재 기본 스타일은 검은 배경·연두색 강조·고정 패널·카드형 컨테이너를 일관되게 사용한다. 다만 Studio는 작업 캔버스가 주인공이어야 하는데 보조 패널이 항상 열린다. 먼저 패널 접기 상태를 기억하고, 빈 상태에서는 필요한 패널만 열며, 선택된 노드·실행 결과·다음 CTA를 강조한다.

`npm run build`는 성공했지만 Vite가 minified JS 637.80 kB에 대해 code splitting 경고를 냈다. 기능 흐름을 정리한 뒤 Studio와 운영 화면을 lazy load하고, 아이콘·렌더러 정보 등 초기 진입에 불필요한 모듈을 분리한다.

## 5. 상태 전이와 화면 계약

### 5.1 일반 작업

`작업 생성 → QUEUED → ASSIGNING → RUNNING → DOWNLOADING → COMPLETED | FAILED | CANCELLED`

각 전이는 다음 계약을 갖는다.

| 전이 | 사용자 행동/시스템 | 권위 기록 | 화면 결과 | 종료·복구 |
| --- | --- | --- | --- | --- |
| 생성 | 생성 폼 제출 | `jobs` insert, 선택 `modal_profile_id` | 큐 행은 `요청 접수` | insert 실패면 큐 행을 성공처럼 남기지 않음 |
| 할당·실행 | worker/Modal | job row와 `job_events` | 계정·단계·경과 시간 | 비활성 계정이면 대체하지 않고 차단 |
| 다운로드 | 원격 결과 수신 | stage와 remote/local path | 다운로드 중, 취소 가능 | 재시도는 새 시도와 기존 결과를 구분 |
| 완료 | worker event | terminal job row, output path | 결과 열기·비용 상태 보기 | 늦은 이벤트가 완료를 실행 중으로 되돌리지 않음 |
| 실패·취소 | worker 또는 사용자 | terminal status와 error | 실패 원인·재시도·로그 | 원격 중단 여부를 별도 사실로 표현 |

### 5.2 Studio 실행

`draft/ready → queued → running → downloading/prepared → completed | failed | cancel_requested → cancelled`

노드 상태(`draft`, `ready`, `running`, `done`, `stale`, `failed`)와 실행 상태는 서로 다른 축이다. 입력 변경으로 `done` 노드가 `stale`이 되는 규칙은 이미 Store에 있으므로(`src/studio/store.ts:167-179`), stale 노드에서 “다시 실행”과 “이전 결과 보기”를 함께 제공한다. 실행 기록이 사라지거나 노드가 삭제될 때 orphan run·asset·cost가 남지 않도록 삭제 정책을 Tauri DB와 맞춘다.

## 6. 단계별 구현 계획

### 0단계 — UX 계약과 검증 기준 고정

목표는 화면을 바꾸기 전에 상태·capability·용어를 하나로 만드는 것이다.

작업:

1. 일반 작업, Studio 실행, 프로젝트, 소재, 연결, 계정, 비용의 상태 사전을 표로 확정한다.
2. `browser preview`, `Tauri`, `offline/reconnecting`, `account unavailable`, `cost pending` capability 행렬을 타입 또는 공통 selector로 만든다.
3. 생성 → 큐 → 결과 → 비용, Studio → 결과 → 내보내기, 연결 → 도구 → 실행의 기준 시나리오를 Playwright/Tauri smoke checklist로 고정한다.
4. 한국어 사용자 상태 문구와 내부 식별자 표시 규칙을 정한다. 기본 화면에는 ID·stage enum·경로를 숨기고 상세 영역에서만 제공한다.

완료 기준:

- 모든 CTA가 `현재 상태에서 가능함`과 `가능하지 않은 이유`를 가진다.
- 각 숫자·badge·상태에 권위 있는 테이블 또는 이벤트 경로가 기록된다.
- 이후 단계에서 화면 문구와 상태 이름을 임의로 새로 만들지 않는다.

### 1단계 — P0/P1 상태 진실성과 데이터 보호

목표는 잘못 실행된 것처럼 보이는 화면과 되돌릴 수 없는 삭제·이탈을 먼저 없애는 것이다.

작업:

1. 브라우저 미리보기의 mutation gate를 적용한다. 생성 제출, 작업 생성, 렌더, MCP/ChatGPT 로그인, 계정·연결·워크플로 저장·삭제를 차단하고 임시 편집만 허용한다.
2. `App.submit`을 durable create 성공 뒤에만 큐에 보이도록 바꾸고, worker event가 없는 브라우저 작업이 `QUEUED`로 남지 않게 한다.
3. worker event 처리 후 해당 작업과 부모 목록을 재조정한다. 앱 재시작·이벤트 누락·늦은 완료·실패·취소를 같은 reducer/loader 계약으로 처리한다.
4. Studio 나가기, 프로젝트 삭제, 연결 삭제, 템플릿·노드·소재·샷 삭제에 영향 범위 확인을 추가한다. 복구 가능한 작업은 undo 또는 보관을 우선한다.
5. 저장 중·저장 실패·dirty 상태에서 나갈 때의 대화상자와 재시도 동작을 추가한다.
6. 고정된 `PIPELINE READY`·`LOCAL CORE`·workspace 표기를 실제 연결 상태와 연결하고, 정상 상태의 구현 세부 정보는 축약한다.

완료 기준:

- 브라우저 미리보기에서 외부 side effect가 발생하지 않는다.
- terminal 작업과 실행은 parent list·badge·cost 집계에도 terminal 상태로 반영된다.
- 삭제·이탈·저장 실패를 한 번의 잘못된 클릭으로 복구 불가능하게 만들지 않는다.

### 2단계 — Studio 핵심 흐름 재구성

목표는 빈 프로젝트에서 결과 후보를 고르는 순간까지의 창작 흐름을 한 작업 공간에서 이해하게 만드는 것이다.

작업:

1. 빈 프로젝트에는 `첫 노드 추가`, `소재 가져오기`, `샷 추가` 중 현재 권장하는 한 CTA를 우선 노출하고 나머지는 보조 행동으로 둔다.
2. 좌측·우측·타임라인·스토리보드 패널의 열림 상태를 저장하고, 좁은 창에서는 한 번에 하나의 보조 패널만 열도록 한다.
3. 노드 카드와 Inspector의 중복 실행 버튼을 정리하고, 실행 버튼 옆에 필요한 입력·계정·연결·비용 상태를 짧게 보여준다.
4. `stale`, `failed`, `prepared`, `cancel_requested`, `cost pending`에 다음 행동을 직접 연결한다.
5. 결과 후보 선택을 노드 결과 목록과 스토리보드 선택 상태가 서로 덮어쓰지 않도록 하나의 선택 모델로 정리한다.
6. 타임라인과 별도 `Edit` 화면의 역할을 확정한다. 하나를 주 편집 경로로 삼고 다른 하나는 명확한 보조 도구로 이름과 진입점을 바꾼다.

완료 기준:

- 새 프로젝트에서 첫 결과 후보를 선택하기까지 사용자 결정이 창작에 필요한 것만 남는다.
- 실행 중에는 중단, 실패 후에는 재시도/원인 확인, 완료 후에는 후보 선택/열기/다음 단계가 보인다.
- 패널이 캔버스 작업을 가리지 않고, 마지막 선택·스크롤·뷰포트를 보존한다.

### 3단계 — 생성·큐·결과를 운영 가능한 하나의 경로로 통합

목표는 단순 생성과 Studio 실행이 같은 운영 규칙을 쓰게 만드는 것이다.

작업:

1. 생성 화면에서 계정 선택 시 workspace, 사용 가능 여부, 마지막 동기화, 예산/실제 비용의 기준을 함께 표시한다.
2. 큐 행을 상세 진입점으로 만들고, 입력 요약·선택 계정·원격 실행·현재 단계·취소·재시도·결과·비용 상태를 한곳에서 제공한다.
3. 결과 화면은 경로보다 파일명·미리보기·생성 시각·상태를 먼저 보여주고, 탐색기 열기는 상세 행동으로 둔다.
4. 일반 작업과 Studio 실행의 결과 소재 등록·비용 귀속·재시작 reconciliation을 공통 selector로 합친다.
5. 사용량 표는 실제 계량, 사용자 설정 예산 잔여, 미확인, 반영 대기를 서로 다른 열/상태로 표시한다. 마지막 정상 값과 동기화 시각을 실패 화면에서도 유지한다.

완료 기준:

- 계정 선택 → 실행 → 큐 확인 → 결과 확인 → 비용 확인이 화면을 잃지 않고 이어진다.
- 같은 workspace가 여러 프로필에 중복 집계되지 않는다.
- 비용을 작업 수로 나누거나 완료 직후 0으로 확정하는 fallback이 없다.

### 4단계 — 연결·계정·워크플로 정보 구조 정리

목표는 연결 등록과 실제 실행 검증을 사용자가 혼동하지 않게 하는 것이다.

작업:

1. MCP 연결, ChatGPT 계정, Modal 워크플로를 별도 탭 또는 명확한 섹션으로 나눈다.
2. 연결 상태를 `저장됨 → 테스트됨 → 도구 확인됨 → 실행 검증됨`으로 표현하고, 각 상태의 다음 행동을 제공한다.
3. 인증 만료·로그인 대기·콜백 충돌·재로그인·취소·실패·재시도를 같은 상태 컴포넌트로 통합한다.
4. 연결·워크플로 삭제 대신 비활성화/보관을 우선 제공하고, 삭제 시 사용처와 저장된 도구가 함께 사라지는지 보여준다.
5. 환경변수 이름만 저장한다는 보안 설명은 유지하되, 반복 문장을 한 도움말 영역으로 줄인다.

완료 기준:

- 사용자는 “등록은 됐지만 실행 검증되지 않음”을 즉시 알 수 있다.
- 인증·연결 장애에서 필요한 다음 행동이 하나로 보인다.
- 삭제가 프로젝트와 비용 이력을 조용히 끊지 않는다.

### 5단계 — 최소 창 크기·접근성·시각 마감

목표는 작은 Tauri 창에서도 핵심 작업을 읽고 조작할 수 있게 하는 것이다.

작업:

1. 최소 창 크기를 제품 계약으로 정하고, 900px·1050px·1280px·최대화 기준으로 Studio와 표 화면을 캡처한다.
2. 전역 `min-width: 1050px` 의존을 줄이고, 사이드바 축소·패널 overlay·표의 열 우선순위·긴 한국어 이름 줄바꿈을 설계한다.
3. `:focus-visible`, 아이콘 버튼 accessible name, tab 순서, 삭제/로그인/실행 대화상자의 포커스 이동과 복귀를 검증한다.
4. 색상만으로 상태를 전달하지 않고 텍스트·아이콘·aria 상태를 함께 제공한다. `prefers-reduced-motion`에서 pulse·timeline transition을 줄인다.
5. 반복 카드·장식용 wrapper·내부 경로 노출을 정리하고, 사용자 결정에 필요한 컨테이너만 남긴다.

완료 기준:

- 지원 최소 창에서 수평 스크롤 없이 핵심 CTA에 접근할 수 있다.
- 키보드만으로 프로젝트 생성, 노드 선택, 저장, 실행, 취소, 삭제 확인을 수행할 수 있다.
- 상태와 오류가 색상·hover·title에만 의존하지 않는다.

### 6단계 — 성능과 회귀 방지

목표는 UX 구조를 고정한 뒤 초기 로드와 장기 유지 비용을 낮추는 것이다.

작업:

1. Studio·운영 화면을 lazy load하고 초기 번들의 637.8 kB 경고를 줄인다.
2. 공통 상태 컴포넌트와 capability selector를 만들고 화면별 임의 문구·임의 로딩 상태를 제거한다.
3. 각 목표 모드에 Playwright smoke 시나리오와 Tauri 수동 smoke 체크를 연결한다.
4. 상태 fixture를 사용해 empty/loading/pending/failed/cancelled/stale/offline/expired-login/cost-unknown 화면을 모두 캡처한다.

완료 기준:

- `npm run build`, worker/renderer 테스트, 브라우저 smoke가 모두 통과한다.
- 실제 Tauri 앱에서 계정 선택, 실행, 재시작, 취소, 늦은 이벤트, 비용 동기화 실패를 확인한다.
- 스크린샷 회귀와 상태 전이 회귀가 같은 PR에서 검토 가능하다.

## 7. 우선순위와 실행 순서

권장 순서는 다음이다.

`0단계 계약 고정 → 1단계 상태 진실성·데이터 보호 → 2단계 Studio 핵심 흐름 → 3단계 생성·큐·결과 통합 → 4단계 연결 운영 → 5단계 반응형·접근성 → 6단계 성능·회귀`

작업 단위는 각 단계 안에서 독립적으로 되돌릴 수 있게 나눈다.

| 우선순위 | 먼저 다룰 문제 | 이유 |
| --- | --- | --- |
| P0 | 브라우저에서 실제 실행처럼 보이는 mutation | 잘못된 성공·대기 상태를 만든다 |
| P1 | 저장되지 않은 변경 이탈, 삭제 즉시 실행 | 데이터 손실과 복구 불가 위험이 있다 |
| P1 | 이벤트 누락·큐 상세·취소/재시도 | 실행 중 상태를 신뢰할 수 없게 만든다 |
| P1 | Studio 패널 계층과 중복 CTA | 핵심 창작 흐름을 방해한다 |
| P1 | 계정·비용·연결 상태의 공통 표현 | 유료 실행과 운영 판단에 직접 영향을 준다 |
| P2 | 반응형·접근성·반복 문구·컨테이너 | 사용성·유지보수 품질을 높인다 |
| P2 | 번들 분리와 시각 마감 | 구조와 상태 계약이 고정된 뒤 최적화한다 |

## 8. 검증 체크리스트

### 브라우저 미리보기

- [ ] Studio에서 프로젝트 생성·임시 편집은 가능하고 저장 범위가 표시된다.
- [ ] 생성·렌더·MCP·ChatGPT·계정·연결·워크플로 mutation은 실행되지 않으며 이유가 표시된다.
- [ ] 작업 큐에 실행하지 않은 `QUEUED` 행이 남지 않는다.
- [ ] 900px, 1050px, 1280px, 최대화 화면에서 핵심 CTA가 보인다.
- [ ] 빈 상태·오류·재시도·읽기 전용 상태가 각 화면에 있다.

### 실제 Tauri 앱

- [ ] 계정 선택이 의도한 Modal workspace에 고정된다.
- [ ] 중지/보관 계정은 다른 계정으로 조용히 대체되지 않는다.
- [ ] 실행 중 앱 종료·재시작 후 작업과 Studio 실행이 올바른 terminal 상태로 복원된다.
- [ ] 완료·실패·취소 뒤 늦은 이벤트가 terminal 상태를 되돌리지 않는다.
- [ ] 실패 후 재시도와 원격 결과 재다운로드가 실제 권위 상태와 일치한다.
- [ ] 비용 동기화 실패는 마지막 정상 값·시각·오류를 보존하고 0으로 덮지 않는다.
- [ ] 삭제·나가기·저장 실패에서 사용자가 영향을 확인하고 복구할 수 있다.

### 접근성·시각

- [ ] 키보드 순서와 포커스 복귀가 프로젝트·노드·실행·삭제 대화상자에서 확인된다.
- [ ] 아이콘 전용 버튼이 스크린 리더 이름을 가진다.
- [ ] 색상 외 텍스트/아이콘으로 상태를 구분한다.
- [ ] 긴 한국어 프로젝트명·파일명·오류가 핵심 정보를 잃지 않는다.
- [ ] reduced motion 설정에서 불필요한 pulse와 transition이 줄어든다.

## 9. 기준 검증 결과

조사 시점의 기준 검증은 다음과 같다.

- `npm run build`: 통과. Vite가 1,787개 모듈을 변환했고 JS 637.80 kB 청크 경고를 냈다.
- `npm run check:worker`: 29개 테스트 통과.
- `npm run check:renderers`: 27개 테스트 통과.
- Playwright 브라우저 미리보기: Studio, 새 작업, 작업 큐, 편집·모션, 결과물, 사용량, 연결 관리, 설정을 각각 열어 스냅샷과 일부 화면 캡처를 확인했다.
- 현재 확인하지 않은 것: 실제 Tauri 창에서의 마우스·키보드 조작, 유료 Modal 실행, ChatGPT 실계정 로그인 완료, 물리 창 크기별 native 렌더링. 이 계획의 완료 기준에서 별도 검증한다.
